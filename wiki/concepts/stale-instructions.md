# 指令文件陈旧(Stale Instructions)

指令文件描述的是**写下那一刻**的代码;代码继续走,文件停在原处。它不是普通的"文档过期":因为文件走**指令**通道、代码走**工具输出**通道(见 [[instruction-hierarchy]]),**过期的描述会赢过正确的实况**。

## 关键信息

- **权威错配是核心**(来源: [[2026-10-22-stale-instruction-files]]):40 个 Python 项目、代码用一种约定、文件要求另一种,320 次运行 → 无优先级声明时 **90.1% 的选择跟随陈旧文件**;Claude Code 在 **79/80** 次里**明确指出冲突**、其中 **86.2%** 仍按文件写(它把代码判为"不合规的一方");Codex CLI 有 **20/80** 次**改写既有代码去迎合文件**(中位删 198 行/9 个文件),恢复原测试后 **17/20 失败**
- **修法很便宜**(来源: 同上):用户级文件加一句"文档与既有代码冲突时以代码为准,并在最终回复里逐条指出不一致" → 跟随代码 4.2% → **91.4%**,改写归零,测试通过 89.4% → **100%**;两个代理都会开始报告冲突(160/160)
- **基础率(转引,待核原文)**(来源: 同上):441 个公司仓库中 **73.8%** 的 AI 配置文件提交一次后从未修改;356 个公开仓库中 **23.0%** 引用了**已不存在的代码**。实例:Supabase 迁 React 19 后,skill 文件连续 **13 天**要求避开 React 19 模式;Codex CLI 自己的 AGENTS.md **24 天**要求更新一份已删除的文档
- **反向证据:公开 OSS 里的文件其实在被维护**(来源: [[2025-11-17-agent-readmes]]):Claude Code 文件 **67.0%** 被多次修改、相邻提交中位间隔约 **1 天**、92% 的抽检提交含实质指令编辑。**与上一条不矛盾**:人群不同(活跃公开仓库 vs 公司内部仓库)。真实分布大概是"活跃项目会改,一次性/内部项目不改"——**尚无同人群对照**
- **为什么"只是文档问题"这个直觉是错的**(来源: 综合):旧 README 误导人,人会用代码反驳它;旧 AGENTS.md 误导代理,**代理受训练去服从它**。所以代价不是"读到坏信息",而是**覆盖正确信息**,并且会**主动改坏能跑的代码**
- **与相邻概念区分**:[[context-rot]] 是"token 越多召回越差"(容量/注意力问题);[[documentation-redundancy]] 是"说了代码已经说的"(冗余问题);本页是"说了代码已经不再是的"(时效 + 权威问题)。三者共同点:文件在**描述代码**,而描述终将失真

## 检测与治理

- **可机械检测**(来源: 同上):引用的路径/符号是否存在(23% 可被一致性检查抓到)、命令是否还能跑、版本号是否与依赖文件一致 → 这类检查适合进 CI(与 [[agent-readability]] 的"知识库新鲜度验证"同构)
- **让代理自己报告**(来源: 同上):优先级句子使代理在每次运行时**输出冲突清单** → 把代理变成文档腐化的传感器,把"报告"接成"修文件"的 PR 就是闭环
- **写"不会腐烂的东西"**(来源: 综合 [[documentation-redundancy]]、[[intent-debt]]):约束(不许做什么、必须用哪个工具)、权衡理由、外部服务入口 —— 而非目录结构、函数清单、当前版本号
- **评审时必须一起看**(来源: [[2026-02-12-evaluating-agents-md]] 与官方实践的合流):改代码的 PR 若让指令文件过时,应把修正作为该 PR 的一部分;否则"写码者不改文档"会把腐化变成默认

## 待办 / 后续

- 缺**同人群**的维护率对照(公开 vs 公司、活跃 vs 沉睡),以及"多久开始误导"的时间曲线
- 缺"腐化 → 质量事故"的量化归因:17/20 测试失败是实验设置下的极端值,真实仓库里陈旧文件的命中率未知
- 与 [[2026-02-12-evaluating-agents-md|ETH]] 的交点:**概览类内容不仅无益(不缩短寻址),还最容易腐烂**(目录会变)——冗余 + 易腐,双重排除
- 厂商侧:若把"代码优先"写进产品默认,本页的多数风险会一次性消解;值得跟踪模型/框架发布说明
