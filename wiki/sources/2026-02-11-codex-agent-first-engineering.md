# 工程技术:在智能体优先的世界中利用 Codex (2026-02-11)

- 原文: `raw/工程技术：在智能体优先的世界中利用 Codex.md`(OpenAI 官网中文版,原文为英文《Harness engineering in an agent-first world》)
- 类型: OpenAI 官方工程博客(**作者 Ryan Lopopolo**;**发布于 2026-02-11**,正文注明;frontmatter `published` 为空)
- 备注: 本 wiki 第十七篇源文档;**首个 OpenAI 视角**——与此前 16 篇(Anthropic ×8、Osmani ×7、Weng、Muratcan)来源阵营齐平;主题:零人工代码的智能体优先工程实验,与 wiki 核心问题("如何让 AI 更好地实现功能")正面相交

## 摘要

OpenAI 团队构建并交付一款软件产品内部 beta 版,**没有一行代码是人工编写的**——应用逻辑、测试、CI、文档、可观测性到内部工具全由 Codex 编写,约为手工编码 1/10 的时间。工程师角色从写代码变为:设计环境、明确意图、构建反馈回路。核心经验:给智能体"地图而非说明书"(AGENTS.md 四败因)、代码仓库即记录系统、以智能体可读性为优化目标、强制执行不变量而非微观管理、吞吐量改变合并理念、熵与垃圾回收的循环清理。

## 关键主张

- **实验与规模**(自述数据):空仓库首提交 2025-08 下旬;5 个月约 100 万行;约 1,500 个 PR;3 名工程师起步(3.5 PR/人/天),扩到 7 人吞吐量反而上升;数百名内测用户;核心理念"不手动编写代码"
- **工程师角色重构**:早期慢不是能力问题而是**环境规范不够明确**;深度优先工作(大目标 → 小构建模块 → 解锁更复杂任务);出问题时解法永远不是"再努力一点",而是追问"缺什么能力、如何让能力对智能体清晰可读又可强制执行"
- **工作流**:人类几乎只通过提示交互;推动 PR 完成 = 指示 Codex 本地自审 → 本地+云端请求多个特定智能体审查 → 响应反馈 → 循环到所有智能体审查者满意(Ralph Wiggum 循环);Codex 直接用标准开发工具(gh/脚本/仓库内技能);**人类可审但不必须——后来几乎所有审核都转为智能体对智能体**
- **应用对智能体可读**:瓶颈变为人类 QA 能力 → 让应用本身可被 Codex 读取——按 git worktree 启动实例(每次更改一个实例)、Chrome DevTools 协议接入运行时(DOM 快照/截图/导航技能)、本地可观测性栈(Vector → Victoria Logs/Metrics/Traces,每 worktree 临时、用完即删)供 LogQL/PromQL 查询——"确保服务 800ms 内启动"类提示变得可行;单次 Codex 运行常超 6 小时(多在人类睡眠时)
- **仓库即记录系统**:"**给 Codex 一张地图,而不是一本 1,000 页的说明书**";大 AGENTS.md 的**四个失败原因**:①情境稀缺(巨文件挤掉任务/代码/文档)②指导过多反而无效(什么都"重要"= 什么都不重要,变成局部模式匹配)③立即腐烂(过时规则坟场、无法判断有效性)④难以核实(单个 blob 不适合机械检查:覆盖率/新鲜度/所有权/交叉链接,漂移不可避免);改为 ~100 行 AGENTS.md 作**内容目录** + 结构化 `docs/`(design-docs 带验证状态、exec-plans 分 active/completed/tech-debt 并版本化、generated、product-specs、references 的 llms.txt、QUALITY_SCORE/RELIABILITY/SECURITY 等);**渐进式披露**严格执行——linter + CI 验证知识库新鲜度/交叉链接/结构,定期"doc-gardening"代理扫描过时文档并发修复 PR
- **智能体可读性为目标**:运行时上下文之外的一切都不存在(Google Docs/聊天记录/人脑均不可访问);Slack 里的架构讨论对智能体 = 迟三个月入职的新员工;偏好能完全内化在仓库内的依赖("枯燥"技术因可组合性/API 稳定/训练集表现更易建模);有时重实现子集比绕过不透明上游更便宜(自研带并发 map 助手:OTel 集成 + 100% 测试覆盖,替代 p-limit 式包)
- **规范架构与品味**:强制不变量而非微观管理——要求边界处 parse-don't-validate 但不指定库;每业务域固定层(Types→Config→Repo→Service→Runtime→UI)、依赖方向严格验证、横切关注点经单一 Providers 接口;自定义 linter(Codex 写的)与结构测试机械执行;品味不变式(结构化日志、命名约定、文件大小限制)以 lint 静态强制,**错误信息写成注入智能体上下文的修复指令**;这种架构通常数百名工程师才推迟——对编码智能体是早期先决条件("有了约束速度才不会下降、架构才不会漂移");中央强制边界、本地允许自主
- **吞吐量改变合并理念**:尽量减少阻塞合并门、PR 生命周期短、偶发测试失败用重跑解决——**纠错成本低而等待成本高**的系统中这是正确选择(低吞吐环境则不负责任)
- **自主水平阶梯**:仓库近期跨过门槛——给定提示,Codex 可端到端驱动新功能:验证状态 → 重现已报 bug → 录故障演示视频 → 实施修复 → 运行应用验证 → 录解决方案视频 → 开 PR → 回应反馈 → 检测修复构建故障 → 仅需判断时才交人工 → 合并;作者明确不承诺泛化
- **熵与垃圾回收**:Codex 复现既有模式(包括不均衡的)→ 漂移;人类手动清理("AI 残渣",周五 = 20% 时间)不可扩展 → 把"黄金原则"(带主观意见的机械规则:倾向共享工具包、不用 YOLO 式探测数据)编码进仓库 + 定期后台 Codex 清理任务(扫描偏差、更新质量等级、开定向重构 PR,多数一分钟内审完自动合并);技术债如高息贷款,小额持续偿还;**"人类的品味一旦被捕捉,就持续应用于每一行代码"**
- **仍在学习**:完全智能体生成系统的架构连贯性如何随时间演变;人类判断力在哪发挥最大作用、如何编码;模型增强后系统如何演变;"构建软件仍然需要纪律,但纪律更多地体现在支撑结构上,而不是代码上";最棘手的挑战 = 设计环境、反馈回路与控制系统
