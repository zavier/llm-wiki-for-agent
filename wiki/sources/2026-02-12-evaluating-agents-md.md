# Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents? (2026-02-12,ETH Zurich)

- 原文: `raw/2602.11988v3.pdf`(arXiv 2602.11988**v3**,2026-09-29)+ `raw/Evaluating AGENTS.md_Are Repository-Level Context Files Helpful for Coding Agents_.md`(v1 HTML,clipped 2026-11-06)

## 摘要(v3 口径)

仓库级上下文文件(AGENTS.md/CLAUDE.md)被代理开发商强烈推荐,却从未被严谨检验。本文构造 **CTXbench**(v1/v2 称 AGENTbench;138 个实例 / 12 个带开发者上下文文件的冷门仓库 / Python),与 SWE-bench Lite 互补,在 4 个代理(Sonnet-4.5、GPT-5.2、GPT-5.1 mini、Qwen3-30B)上跑三条件(NONE / LLM 生成 / 开发者编写)。**v3 结论:提供上下文文件总体上不提升任务成功率**,而成本平均 **+20% 以上**;这一观察对**生成物与开发者手写两种文件都成立**。指令被很好地遵循,但**仓库概览虽然流行且被厂商推荐,却无用**。作者收束:上下文文件对**说明非标准实践**有用,但任何“为了提升性能”的改动**都必须先被严谨评测**。机制侧另有:文档冗余假说(删掉仓库全部文档后生成物反而 +2.7% 并胜过人写)。

## 关键主张

> [!warning] 版本历史:v1 的「-3% / +4%」已被 v3 取代
> **v1(2026-02-12)**:摘要 “LLM 生成 -3%、人写 +4%”;正文 §4.2 “SWE-bench Lite -0.5% / AGENTbench -2%”。**v3(2026-09-29)**:基准改名 **CTXbench**;摘要改为“**不普遍提升成功率**,对两类文件都成立”;正文人写文件从 +4% 降为 **+2.4%(p=21%,不显著)**,但**相对生成物高 7%(p=3.8%,显著)**。→ 既在 wiki 多处引用的“人写 +4%”**作废**;“-0.5%/-2%”仍成立(只在生成物条件)。本页下列数字已按 v3 校准。

**基准:CTXbench(原 AGENTbench)怎么造**(来源: 同上):GitHub 搜索含根目录 AGENTS.md/CLAUDE.md 的 Python 仓库 → 要求有测试套件 + ≥400 PR(保证能抽出 ≥10 个实例)→ 5694 个 PR 过滤为 138 实例(12 仓库)。多数 PR 不含测试,故用 LLM agent 生成回归测试并**验证 fail@R、pass@R∘X\***,人工筛掉过拟合实现的断言,最终测试对改动代码的平均覆盖 **75%**;任务描述用第三个 LLM 标准化成 6 段(描述/复现步骤/期望/实际/规格/附加),随机抽检 10% 确认**无解法泄漏**;保留 87% 候选(至少一个测试通过)。实例画像:issue 211.6 词、代码库 3337 文件、patch 118.9 行 / 2.5 文件、**上下文文件 641 词 / 9.7 个小节**。

**主结果:生成物降成功率、抬成本**(来源: 同上,v3 正文):8 个设置中 5 个成功率下降;平均 **-0.5%(SWE-bench Lite)/ -2%(CTXbench)**;步骤 **+2.45 / +3.92**,成本 **+20% / +23%**。逐模型(Table 2,SWE-bench Lite,步数/美元):Sonnet-4.5 54.4/$1.30 → 57.2/$1.51;GPT-5.2 12.5/$0.32 → 12.7/$0.43;GPT-5.1 mini 40.9/$0.18 → 45.2/$0.22;Qwen3-30B 29.7/$0.12 → 32.2/$0.13。

**人写文件:v3 已下调为不显著**(来源: 同上,v3):相对无文件,人写平均 **+2.4%(p=21%,不显著)**;但**显著优于生成物**:高 **7%(p=3.8%)**。四个代理中**除 Claude Code 外均提升**;代价 **+3.34 步、成本最高 +19%**。CTXbench 上 Sonnet 46.5(LLM)→ 45.3(Human)步、1.33 → 1.30 美元。→ v1 摘要的“+4%”为**已被取代**的旧口径。

**上下文文件不是有效的仓库概览**(来源: 同上):度量"首次触碰 PR 改动文件前的步数",有无文件**无实质差别**(两基准皆然)。概览的供给并不缺:被 GPT-OSS-120b 判定含概览段的比例为 Sonnet-4.5 生成 **100%**、GPT-5.2 **99%**、Qwen3-30B **95%**、GPT-5.1 mini **36%**;12 份人写文件里 8 份有概览、4 份逐目录枚举。**副作用发现**:GPT-5.1 mini 在文件存在时会**多次发命令去找上下文文件、并反复重读它——尽管它已在上下文里**;此行为只在有文件时出现,是该模型步数暴增的直接原因。

**指令被遵循——所以失败不是"没听话"**(来源: 同上):文件提到 uv 时每实例平均用 1.6 次,未提到时 <0.01;仓库专属工具提到 2.5 次 vs 未提到 <0.05;几乎全部被测工具呈同向。工具**意图**分类(GPT-OSS-120b,334 类归并为 10 类)复核:测试、搜索、质量检查显著上升。

**照做更费思考**(来源: 同上):GPT-5.2 reasoning token **+22%**、GPT-5.1 mini **+14%**(SWE-bench Lite;AGENTbench 14%/10%);人写文件 +20%/+2%。作者据此认为**多余要求把任务变难了**,而非模型忽略要求。

**文档冗余假说(消融)**(来源: 同上):手动删掉仓库内所有 `.md`、示例代码与 `docs/` 后再评测(Claude Code 因成本排除)——LLM 生成文件**一致提升 2.7%** 且**反超人写文件**。解释:LLM 文件与既有文档高度冗余;只有当它成为**唯一文档来源**时才有价值。这也解释了"加了上下文文件感觉变好"的轶事——多数冷门仓库几乎没有文档。

**更强模型生成的未必更好;提示也没那么重要**(来源: 同上):改用 GPT-5.2+Codex 生成文件,SWE-bench Lite 全模型 **+2%**,CTXbench 全模型 **-3%**;Codex 与 Claude Code 的生成提示互换后无一致优劣。

**按仓库看没有显著效应**(来源: 同上):12 个仓库逐一比较,无一仓库出现显著影响;CTXbench 难度分布均衡(验证构法),SWE-bench Lite 则因 django 占多数而估计噪声大。

**实验设置要点**(来源: 同上):Claude Code 开 Task 工具(Haiku-4.5 子代理);温度 0(Qwen 0.7/top-p 0.8,60% 压缩,shell 输出限 2000 token);每实例采样一次;CTXbench 容器为 Docker,**移除 git 历史与全部 remote**,给联网;人工核查**无作弊**(去看对应 PR),联网调用 <1%。

## 待办 / 后续

- ✅ **v1 → v3 差异已核**(2026-11-06):基准改名 CTXbench;人写 +4% → **+2.4%(p=21%)**;新增“相对生成物 +7%(p=3.8%)”;摘要结论改为“不普遍提升”
- 未核:v2(2026-06)是否还有独立于 v3 的中间口径;若有人引“+4%”或“AGENTbench”,可判定为引 v1
- **纯 Python 是最大外部效度缺口**:作者自认 Python 训练语料充足,模型参数知识可能已覆盖工具链/仓库惯例,从而**低估**上下文文件在冷门语言/私有栈上的作用——这恰好是我们(私有仓库 + 非主流栈)最该关心的方向,缺数据
- 未测:安全性与代码效率(只测任务完成率)、多轮/长时任务、上下文文件与 hooks/skills 的替代关系
- 可跟进:作者呼吁的"原则性地自动生成简洁、任务相关的指导"(continuous learning from prior tasks 方向)是否有后续论文
- 与 pi(极简 harness)的关系:本文为"少配置"提供实证,但 pi 的对照实验是"零 AGENTS.md",本文的 NONE 条件同样接近零配置——两者并不冲突
